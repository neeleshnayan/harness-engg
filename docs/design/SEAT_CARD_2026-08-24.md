## The five questions a seat card answers, and where the data stands

1. **NOW — what are they working on.** Current dispatch headline + elapsed,
   or idle (idle is a feature, render it calmly). DATA: exists (dispatch
   state, run records); D33 (live fan-out) extends it to sub-agents.
2. **TRIGGER — what fired it.** A lineage chip chain, newest first:
   dispatch ← request/finding ← approver/instruction. Every chip clicks
   through to its record. DATA: partially exists — `serves_requests` +
   requests' `actor`/approval events give the chain WHEN filings declare
   them (4/125 runs did; the routing door now enforces on opt-in). The
   projection must render an honest "lineage undeclared" for old rows,
   never a guessed chain.
3. **LEDGER — the ROI, teamwide-comparable.** Three tiles: spend this run/
   day, what it bought (verdicts/kills/candidates/merges), findings per
   Mtok vs team. DATA: token counts exist on most runs; the per-seat meter
   is Grace's proxy with HER recorded caveats (kind is free text; chair
   tokens absent) — the tile carries her caveat line until her instrument
   lands. Absence renders absent, never zero.
4. **LEARNINGS — what came out of it.** The last run's headline lessons +
   the propagation edges (binds sent → seats; evolves applied). DATA: today
   this is prose in seat memories. GOING FORWARD the run-record filing
   gains optional structured fields — `lessons[]` (headline strings),
   `binds_sent[{seat, headline}]`, `evolve_applied` — mirroring the
   request schema; prose STATE remains the full record. The card renders
   the structured fields; old runs render "in the seat's memory" with a
   link.
5. **BOOK OF WORK — pending, with the assigner.** The seat's in-tray:
   each item with who assigned it (request actor / CEO trigger / chair)
   and its queue state (queued/deferred/standing-trigger). DATA: exists
   (requests carry `serves` + `actor`); needs only the per-seat projection.

## Spine deliverables (the projection layer)

- `GET /fund/floor/seats` (or extend the existing floor payload): per seat
  — now{}, trigger_chain[], ledger{}, learnings{}, book[]. All fields
  nullable with a reason; the projection never invents lineage or zeros.
- Run-record filing door: the three optional structured fields above.
- The lineage chain resolver: serves_requests → request → approval event →
  quoted instruction, materialised at read time from the log.

## Visual grammar

Inherits theme.ts's ILLUMINATION PRINCIPLE and the request-card rules:
calm, type-and-space hierarchy, colour only where semantic (working state,
learnings marker), sentence case, mono for ids. One card per seat in the
rooms grid; the executive row (Vishesh, Grace, Donna) wears the same card —
no special chrome, their difference is their content.
